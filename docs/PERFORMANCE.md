# Electron 性能与交互实测

真实 Electron 生产构建完成三轮探测：首轮 **32 项检查全部通过**；第二轮与优化后第三轮均 **33 项检查全部通过**，三轮退出码均为 0。优化后末期 renderer JS 已用堆从 225.1 MiB 降至 78.1 MiB，但 renderer 工作集仍为 403.5 MiB，主进程 resident 为 577.0 MiB。交互检查通过与堆内存改善不能解读为所有进程内存目标已满足。

探测脚本：[performance-probe.cjs](../scripts/performance-probe.cjs)。完整证据：[首轮 JSON](../artifacts/performance-2026-10-12T22-34-51-614Z/report.json)、[第二轮 JSON](../artifacts/performance-2026-10-12T22-39-58-522Z/report.json)。

## 环境与方法

- 两轮时间：2026-10-12 22:34:51–22:35:03、22:39:58–22:40:14 UTC；Windows x64，Intel Core i7-12650H，16 个逻辑处理器。
- Electron 35.7.5、Chromium 134.0.6998.205；同一生产构建的 `file:` 页面，首窗实际可见。主 JS SHA-256 为 `9e633676bb7aeb612783401e1a13daaacafbe1555ed9979bcedd4adda1dca397`，构建资源修改时间为 22:31:19 UTC。
- 使用全新临时用户目录，在写入前通过真实 `app.info` 核验隔离路径；正常用户目录未写入。两轮退出时 Electron 均已关闭，临时 SQLite 库和音频文件已删除。
- 测试库含 10,000 个符合生产 `Track` 结构的合成条目，序列化状态为 4,186,310 字节。歌曲名、艺人和专辑是明确的性能 fixture，不是在线曲库内容，也不会作为产品默认数据显示。
- 生成真实 180 秒 WAV，通过生产 `files.import` 导入和授权，再由生产播放服务读取。其余 fixture 共用该测试文件路径，避免网络波动或不存在的音频影响交互计时。
- 保存、加载和设置更新均经正式 IPC 与 SQLite worker。导航使用真实按钮，筛选与键盘使用 Playwright 实际输入。滚动测量包含 `requestAnimationFrame` 更新。
- 没有目视审查截图。正常性能测量不强制 GC；第二轮末尾另外加入明确标记为诊断用途的主进程／renderer 强制 GC 快照，不能当作常态内存指标。

## 内存证据与待优化项

第二轮正常运行快照如下；CDP 堆值与 Electron 进程内存使用不同口径，明确分列：

| 阶段 | CDP renderer JS 已用堆 | 主 Node 已用堆 | 主进程 resident | Renderer 工作集 | DOM 节点 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 初始空库 | 4.9 MiB | 10.6 MiB | 123.1 MiB | 95.3 MiB | 278 |
| 万条歌单 | 68.4 MiB | 36.7 MiB | 285.8 MiB | 215.4 MiB | 630 |
| 播放＋队列打开 | 84.0 MiB | 30.8 MiB | 308.6 MiB | 341.8 MiB | 954 |
| 导航与四组语言／主题截图之后 | **225.1 MiB** | 101.1 MiB | 521.2 MiB | **744.2 MiB** | 287 |

进程数据来自 `getProcessMemoryInfo()` 与 `app.getAppMetrics()`，原字段单位为 KiB；CDP 与 Node 堆原字段为字节。工作集包含原生内存、运行时、图形、缓存等，不能等同于 JS 堆，也不能把多个进程的共享页简单相加。主进程 resident 包含 worker 所在进程的开销；主线程 `process.memoryUsage().heapUsed` 不能代表 SQLite worker 的全部堆。

第二轮另外对 renderer 使用 `HeapProfiler.collectGarbage`，对主线程使用 V8 暴露的 GC，得到独立诊断快照：

| 诊断项 | GC 前 | GC 后 |
| --- | ---: | ---: |
| Renderer JS 已用堆 | 236,063,404 B | **218,633,996 B（208.5 MiB）** |
| 主线程 Node 已用堆 | 105,966,596 B | 25,005,824 B（23.8 MiB） |
| Renderer 工作集 | 744.2 MiB | 497.6 MiB |
| 主进程 resident | 521.2 MiB | 569.7 MiB |

GC 后 renderer 仍保留较大堆；主线程垃圾明显回收，但主进程 resident 没有同步下降，说明不能仅将高进程内存解释为主线程可回收垃圾。这个短时快照尚不足以认定泄漏，也不是常态用户内存指标。**第二轮数据不支持宣称万条库＋队列＋繁体界面能保持 renderer 低于 200 MiB；第三轮改善与当前限制见下节。**

`performance.memory` 给出的近似固定 10,000,000 字节不用于上述结论；最终报告采用 CDP `Runtime.getHeapUsage`。

源码审查得到的候选优化点如下，它们是有代码依据的建议，不是已完成 heap snapshot 的对象占用排行榜：

1. [store.ts](../src/renderer/src/store.ts) 对 library、queue 等使用深度、同步监听，并在变更后将整库与播放器队列 JSON 化保存；库替换、设置更新和队列拷贝会扩大 Vue 深度依赖及整库快照开销。建议缩小变更域，合并设置更新，把进度持久化与整库保存分开。
2. [library.ts](../electron/main/services/library.ts) 的 get／mutate／save 路径多次 clone 与 normalize 完整状态。建议减少同一事务的全库复制，优先复用未修改的不可变歌曲数据。
3. [sqlite.ts](../electron/main/services/sqlite.ts) 同时保存完整 `state` JSON、完整歌单 JSON 形式的 `listsHash` 和规范化 tracks 表，再通过 `db.export()` 导出整个数据库。建议将 `listsHash` 改为真正摘要，减少重复 metadata，并避免纯进度／设置更新重复整库导出。
4. 繁体切换、整库设置事件、OpenCC 构造与截图都发生在末期高内存快照之前，现有采样不能将增长独立归因于其中某一项。应进一步在各次语言切换前后采样，做稳定期与对象保留分析；不要直接将全部增长归咎于词典。

## 复测

先完成生产构建，然后运行：

```powershell
node scripts/performance-probe.cjs
```

Node 不在 PATH 的本机可使用用户指定的 bundled Node。脚本不自行构建、不修改 `out` 或 package，运行期间不要重建输出。`PERF_OUTPUT_DIR` 可指定证据目录；`PERF_TRACK_COUNT` 可指定条数，默认 10,000、上限 50,000。任何交互检查失败都会写入 JSON 并以非零退出，同时继续其他独立检查；内存快照当前作为记录与诊断，没有隐藏的低内存通过阈值。
